A mount is a metadata namespace with an explicit allowed Kubernetes namespace set. A normalized logical path belongs to one mount and maps to one exact native Secret namespace/name. Each document has an explicit field-name-to-native-data-key mapping, supporting both scalar references and grouped key/value documents. Groups manage at most 64 selected keys in the same Secret. Logical field names default to the original native key spelling; scalar aliases keep their exact namespace/name/key. There is no underscore splitting, target inference, or automatic alias adoption.

SQLite stores mount/path IDs, mappings, policy grants, operation/rotation metadata and audit records. A unique active mapping prevents two engine paths from owning the same native namespace/name/key; disjoint groups may share a Secret. Native resourceVersion serializes their updates. Canonical objects retain unrelated keys, type, labels, annotations, owners and managed fields. Typed or immutable Secret constraints are respected. Removing managed keys keeps the Secret and an empty data object; deleting a last required typed key fails rather than changing the type.

Path segments use one validated normalized representation. Empty/dot segments, ambiguous encoded separators and inconsistent Unicode representations are rejected before policy evaluation. Prefix grants match complete segments: `apps/api` does not grant `apps/apiculture`. Routes identify registered paths by opaque UUID; display paths remain metadata.

The 603 reported legacy aliases across 12 namespaces remain available with their original spellings and explicit targets. The existing 18-namespace allowlist/Roles are not reduced. Adoption is explicit and value/history changes require current native resourceVersion. Registered engine targets additionally pass policy checks on flat reveal/CRUD and alias lookup so those routes cannot bypass policy. Aliases themselves contain no values. Dedicated engine history objects are hidden and denied on flat native/alias routes, even if the operator accidentally includes their namespace in the ordinary allowlist.

## Native current and history ownership

Current values remain in the existing canonical Secret's data. One owned `bortus.io/kv-state` annotation records path IDs, selected key mappings, committed version references, head version, operation IDs and tombstone state. Public metadata uses a named-field whitelist; arbitrary annotations, managedFields, API exception bodies and last-applied configurations never enter responses, audit, UI or history.

Immutable version Secrets live in an externally created dedicated history namespace. They contain only the selected document fields, encoded as native Secret data, plus minimal owned identity/version/operation metadata. They never clone the canonical object's metadata or unrelated data. Scalar/binary imports retain original key spelling and bytes; a history/export operation cannot reveal another key in the source Secret. Cross-namespace ownerReferences are not used. Ownership is verified by path/operation/source namespace/name/UID bindings and referenced history UID, rather than a label alone.

The default retention is 20 committed versions per path, with an operator maximum of 100. Total decoded managed values are bounded to 256 KiB per document and JSON request bodies to 512 KiB. Canonical replacement JSON must fit a conservative 900-KiB object ceiling and the owned annotation must fit 200 KiB; Kubernetes remains the final authority for its 1-MiB Secret and annotation limits. Oversized objects fail before mutation; no truncation or splitting creates misleading versions.

Creating a new path first registers metadata intent and creates a minimal owned Opaque canonical Secret with empty data. This establishes a source UID. It then performs the same versioned CAS protocol as an adopted object. A failure can leave a recoverable empty object or pending registry intent; it is reported explicitly and does not claim that credential values were committed. Existing-object adoption snapshots selected current fields as version 1 and CAS-adds the native state annotation without altering their values.

## CAS, history and ambiguous outcomes

Native request schemas now accept the engine's existing optional pathRevision prerequisite as a positive safe integer. New UI clients send their captured path revision with the required native head/resourceVersion; stale metadata is rejected before mutation. Existing clients without this additive field retain their head/RV contract and commit-time fresh metadata checks. Schema and creation/adoption/update HTTP regressions passed without native writes on stale revisions; this adds no migration or native format change.

Update policy authorizes explicit complete replacement independently of read. A no-read UI mode must fetch metadata only, require entered replacements and clearly confirm removal of omitted mapped fields. Preserve-existing-values editing requires read. Server-internal reads for drift/CAS never become caller value access.

Prior committed or unresolved operations prevent initial activation when the canonical object/ownership marker is missing. The app does not reset that path to version one or treat a committed mapping as an unadopted legacy alias. It reports explicit recovery instead. A still-owned empty source left by failed first creation can be resumed with a fresh CAS only when it has no prior committed values; original history candidates remain intact.

First native creation and existing-object adoption additionally require effective engine administration. A scoped create policy may register metadata intent, but cannot bind arbitrary pre-existing credentials to a new logical path and thereby bypass other scopes. An administrator explicitly approves the exact native target by performing its initial creation/adoption; subsequent values/history operations use fresh action policy. Candidate CAS, drift checking and operation recovery passed local synthetic native protocol checks; their public human routes passed local production HTTP/TLS qualification.

Native state helpers are implemented locally. The owned canonical annotation holds at most 64 disjoint groups, 100 retained references and 100 recent operation markers per group; oversized ownership state fails before replacement. Marker pruning never proves an unresolved operation failed: if its proof has disappeared, resolution remains recovery-required/ambiguous. Field values use explicit arrays and exact JSON maps, including valid `__proto__`, `constructor` and `toString` keys. Ten focused native protocol tests and the full 69-test suite passed. The expanded suite now passes 70 tests including bridges and missing-marker recovery; production public-route/TLS checks passed. Image and live-native qualification remain pending.

An update creates a new immutable candidate history Secret, then replaces the canonical Secret once with both selected data and its committed history reference in a single resourceVersion CAS. The candidate represents the prospective version, never an unrelated-key snapshot. Only a referenced candidate is committed history. A failed/conflicting CAS leaves a candidate for explicit recovery or garbage collection; it cannot become the displayed head. Rollback creates a new version and uses this same CAS, preserving immutable older versions.

Native reads compare selected current bytes with the committed head in memory. External drift is a 409 reconciliation requirement, never a silent version assignment or value hash persisted to SQLite. Explicit reconcile captures the external selected values into a new version with fresh CAS. An unrelated-key change merely changes resourceVersion; stale writers still receive conflict and must refresh.

Operation IDs distinguish `pending`, `committed`, `conflict`, `ambiguous` and `recovery-required`. A timed-out create/replace is read back by owned operation ID, history reference and UID. Read-back failure remains ambiguous; neither automatic overwrite nor a blind second mutation is permitted. Native annotation/reference state resolves SQLite operation metadata after a restart. Missing/replaced/unreachable canonical objects are recovery conditions, not permission to delete their potential last history copies.

An unverifiable successful PUT response also enters read-back/recovery; a malformed or changed ownership response never proves that the native write failed. This refinement passed local unit and production HTTP/TLS qualification.

GC commit additionally requires the exact recorded path/target/version operation ID behind each candidate. Missing operation ownership retains history rather than deleting a possible recovery copy. Preview eligibility is metadata-only; full immutable/value/operation validation happens before the source fence.

Destroy first CAS-removes a non-head committed reference, then deletes only a verified owned history Secret with UID/resourceVersion preconditions. Active head destruction requires a prior tombstone. Retention drops references in the canonical CAS before garbage collection. Partial cleanup is reported separately from the committed value operation. Garbage collection requires an explicit preview/confirmation, a 24-hour minimum orphan age and rechecks of all current references and source UID. No startup sweep or blind background deletion occurs.

Destroy and per-path administrator GC APIs passed local unit and production HTTP/TLS qualification. A tombstoned head can become head zero while its sequence remains monotonic; later writes create a new version. GC previews use mandatory PartialObjectMetadataList negotiation, 100-object pages, a 15-second/10,000-object/eight-MiB list bound and at most 100 selected histories. Commit rechecks full immutable owned history, current head integrity and current source UID/all group references, then CAS-fences the source before deletion so an older in-flight app CAS cannot attach a deleted candidate. Native deletion has UID/RV preconditions and never targets canonical Secrets. A 30-second/abort boundary stops further cleanup; already-started native work uses its ordinary deadline/recovery protocol. Reference commit and cleanup outcomes are reported separately, without rollback or automatic retry.

Audit contains actor/identity ID, operation ID, action, exact metadata target, previous/new version and outcome only. It contains no values, base64 payloads, diffs, request bodies or value digests. Audit insertion failure prevents a new operation before native mutation; a post-write audit/update failure is recovery-required, with the native operation marker retained. Public errors are fixed strings. The synthetic different-key last-applied annotation regression is required for current metadata, history, audit, import/export and UI.

## Human policies and automation identities

Current DB roles remain authoritative: readonly sees permitted metadata, never values or mutations. Engine grants restrict write users by mount/path/action with explicit deny overriding allow. Actions are list/read/create/update/delete/rollback/reconcile/destroy/export/rotate. Engine administration manages metadata, policies and identities; it does not mint a broader Kubernetes service account.

Effective engine administration also gates infrastructure and peer identity capabilities that could bypass path policy: peer password/role/flag/deletion, shell/pod execution, arbitrary YAML reads/replacements, logs/provisioning output and Flux/workload/configuration mutations. A scoped writer can reset only their own password and use granted KV operations. Existing write accounts receive the flag through the forward migration. Out-of-band Kubernetes/host administrators and externally controlled workloads remain trusted; application policies do not isolate against those principals. Merely hiding UI controls does not enforce this boundary.

A forward `User.engineAdmin` migration grants the flag to existing writers, preserving operator access. Subsequent accounts default false, with the first bootstrap writer true. Effective administration requires both the flag and a current write role. Policy/account mutations use the existing serialization transaction and preserve at least one effective engine administrator as well as the existing last-writer invariant. Policies cannot grant readonly users write/value privileges.

Automation tokens have a distinct opaque `bortus_kv_v1_<id>_<256-bit-random>` prefix/audience, a one-time displayed secret, hashed authentication material in SQLite, an expiry no later than 30 days, and explicit revocation. Their effective rights are token policy intersected with the owning user's fresh role/policy; deletion/reset/session-version change or demotion of the owner revokes their authority. They are neither session JWTs nor engine-admin identities. Middleware permits only the exact automation KV entrypoint, whose handler validates this distinct token and policy before native access. Tokens cannot become human cookies, legacy lookup credentials or arbitrary shell credentials.

The externally supplied `BOTRUS_SECRETS_KEY` retains its existing legacy lookup audience and exact aliases. It authenticates a named `legacy-lookup` service principal, never an engine administrator or automation-token issuer. Unadopted aliases retain their existing native lookup behavior. Explicit adoption registers read-current grants for already-resolved aliases to the selected keys; this metadata-only compatibility grant preserves existing consumers and is shown in the adoption preview. It does not grant grouped sibling fields, history, writes or engine API access. Every adopted alias lookup evaluates this principal's exact-key grant and explicit path denies before reading a value; disabled/revoked grants fail closed. Policy changes show affected legacy aliases before commit rather than silently breaking consumers. Newly introduced aliases need an explicit grant on adopted paths. Missing policy data is denial, never the old privileged fallback. Tests cover all 603 alias spellings, grouped sibling isolation, explicit deny/revoke, post-adoption alias addition, unavailable policy storage and attempts to use the legacy key at other token audiences. Logs, audit and browser persistence never retain presented tokens; responses carrying values or tokens are no-store.

An old flat-writer image cannot enforce new adopted-path policies. Recovery therefore uses a previously validated KV-compatible image and matching forward schema, with independently protected metadata/native backups. This closes both old-image-on-new-principal and leftover-old-principal paths. An old flat image on a recovery principal receives no native Secret get/list/create/update/delete rights, so it cannot reveal or edit adopted values. It is not a supported ready KV recovery deployment. No app executor changes live RoleBindings or admission state.

## Kubernetes constraints checked

The old principal must also lose pod exec, workload create/update/patch and comparable credential-reaching infrastructure capabilities; revoking only Secret verbs would still permit mounting adopted values or extracting the new ServiceAccount token. Delivery must move required capabilities to the guarded KV principal and revoke the old app management bindings, proving denial of direct Secret access **and** exec/workload mutation. Old images cannot open the post-migration metadata PVC either: their legacy peer-password/role APIs could alter the shared account database and impersonate a broader-policy user in the new app. The enforced compatible-digest rule therefore also covers any app Pod/controller template that references the protected SQLite claim, regardless of ServiceAccount, including every regular/init/ephemeral container. Delivery must prove old-image/PVC admission denial and absence of a pre-existing old-image mount before adoption. Only a validated KV-compatible image may read/write the migrated metadata database. Trusted out-of-band cluster/host/storage administrators remain outside this application isolation boundary. These are external rollout prerequisites, not locally verified installation claims.

Source-inspected protected resources in the delivery charts checkout are namespace `bortus`, SQLite claim `bortus-data`, runtime Secret `bortus-runtime` (keys `jwt-secret` and `lookup-token`), and the proposed guarded ServiceAccount `bortus-kv` replacing `bortus`. These names were read from `charts/bortus/values.yaml`, not verified live. The compatible-image rule must cover protected credential references via env secretKeyRef, envFrom secretRef, direct Secret volumes and projected Secret sources, as well as the protected claim, regardless of principal. Check all regular/init/ephemeral containers and controller templates; mutable tags/labels or choosing the default/old principal cannot bypass this guard. Add any externally supplied operator kubeconfig/credential Secret to the protected reference set. A kubelet-injected runtime lookup token would otherwise let an old image use the new app's legacy lookup audience even after its direct Secret/exec/workload permissions were revoked. Delivery's negative cases must include each reference form and prior old-image mounts/credential exposure; local flag/unit evidence is insufficient.

The design follows the documented [Secret size/immutable constraints](https://kubernetes.io/docs/concepts/configuration/secret/), [same-namespace owner rules](https://kubernetes.io/docs/concepts/architecture/garbage-collection/), [annotation-size validation](https://github.com/kubernetes/apimachinery/blob/master/pkg/api/validation/objectmeta.go) and [UID/resourceVersion delete preconditions](https://github.com/kubernetes/apimachinery/blob/master/pkg/apis/meta/v1/types.go). BORTUS's lower body/object/retention limits are explicit application design choices.
